# Native visual compatibility and port priorities — 2026-11-03

The first useful step is to try the unchanged priority packs against the new native loaders, rather than translate the entire Java EMF/ETF mods. Those loaders already cover substantial parts of Fresh Animations, connected textures, fonts and sounds. Their presence does **not** establish visual parity for this setup. Unsupported state, configuration and render paths need separate, narrowly scoped ports.

This is a read-only source and staged-asset audit. No game, build, tests, installation, original-instance edits or device profiling were performed by this unit. Parent-owned benchmarks run separately.

## Configuration and performance gaps

The original EMF config enables all models but uses `modelUpdateFrequency:Average`, animation LOD distance20 and shadow-pass animation skipping. No equivalent native configuration was established. The f42 VM preserves per-frame variable-state semantics, **but still evaluates the expression steps on each draw**; this is not proof of cached poses or shadow-pass skipping. Its expression and saved-entity bounds prevent unlimited growth, but actual CPU cost with this pack still needs measurement. [per-draw evaluator](https://github.com/horizon-rust/horizon/blob/f42ef42ef6ceccb3c6a20bea2481d87949a51c81/crates/horizon-client/src/mobs/cem_anim.rs#L447).

ETF's original config has blink length1 and frequency150. Native defaults are5 and150, with per-texture properties able to override them. This is a genuine configuration-conversion pattern **only when a matching blinking texture exists**. Do not emit unnecessary overrides for the three inspected FA packs, which have none. A future private overlay could supply a missing `blinkLength=1` property while preserving existing per-texture overrides and original bytes/provenance. [native defaults and parser](https://github.com/horizon-rust/horizon/blob/f42ef42ef6ceccb3c6a20bea2481d87949a51c81/crates/horizon-optifine/src/blink.rs#L20).

1. **Priority unchanged-pack compatibility profile.** Start with Fresh Animations, its extensions and harness in their existing relative order; then add the two CTM packs; then Icons/font/weather sounds. Use a fresh isolated profile, original source hashes and full-scene readiness. Keep every omitted layer explicit: a subset is diagnostic, not the final appearance baseline. Inspect CEM warnings before measuring speed. Acceptance includes adult/baby mobs, walking/attacking/sleeping/grazing, equipment, reload and the known missing extension chest animation. No Java-mod port is required to try these native data paths.
2. **Converter CEM preflight, before code generation.** Resolve JEM/JPM dependencies and texture references; inventory expression targets, parameters, functions and configuration requirements against a versioned target-capability record. Flag stubbed parameters, unused `render.*`, unknown targets/names, bounds reached and missing files. A lexical scan may nominate gaps but cannot prove expression parsing/binding. The actual zombie animation sample uses the ordinary supported function family, including `if`, trigonometry and clamping; that does not prove all parts or all261 paths work. Keep detailed evidence and one actionable task per missing capability.
3. **Smallest real behavior port: chest CEM animation.** Start at `block_entity_cem` plus the block-entity renderer. Reuse the expression machinery through a block-entity-specific context, rather than invent mob state. Needs stable per-position/dimension state, vanilla lid-pose inputs and reload cleanup. Test single/double/trapped/ender chests opening/closing with multiple instances. `native_block_entity_submit` is for **mod-owned** block entities; it is not a verified interception hook for vanilla chests. This likely needs an engine/source integration, not a data-only carry. [hook boundary](https://github.com/horizon-rust/horizon/blob/f42ef42ef6ceccb3c6a20bea2481d87949a51c81/crates/horizon-client/src/game/native_hooks.rs#L2932).
4. **Performance port only after appearance passes.** Investigate world-pose reuse across repeated same-frame draws and the user's Java animation-LOD policy. Preserve GUI versus world behavior, global variables, multiple entities, shadows and model reloads; first demonstrate equivalent poses. Do not simply stop updating distant mobs or call it quality-neutral without comparison.

## Layer and native-build contracts

Keep complete ZIPs and their metadata. Native filters/format overlays apply before the resource tree is assembled; fonts, sounds, atlases, languages and blockstates have different merge rules. Flattening everything as a last-file-wins dictionary loses semantics. The preserved53-layer selection also does not, by itself, establish the implicit Fabric mod-asset order or activation of the210 separate asset-only candidates. Those need explicit provenance/order decisions. [overlay construction](https://github.com/horizon-rust/horizon/blob/f42ef42ef6ceccb3c6a20bea2481d87949a51c81/crates/horizon-client-render/src/packs.rs#L605).

Native behavior ports remain Rust/mixin builds, not execution of Java classes. The current contract lets **hook-only** bundles declare a minimum `hooks` level: a later supported API can build an older hook-only bundle, while its `horizon` field records the tested revision. That is not blanket permission to ignore private-field dependencies or source overwrites. Build and behavior acceptance remain necessary. `native_client_resources_reloaded` is a verified reload notification, **not initial startup**; use it appropriately for caches. [build/pinning contract](https://github.com/horizon-rust/horizon/blob/f42ef42ef6ceccb3c6a20bea2481d87949a51c81/docs/native-mods.md#L58), [reload hook](https://github.com/horizon-rust/horizon/blob/f42ef42ef6ceccb3c6a20bea2481d87949a51c81/crates/horizon-client/src/game/native_hooks.rs#L2087).
