Set `maxFps:60` / `enableVsync:false` in options.txt and `framePacing:efficient` versus `framePacing:precise` in horizon-graphics.txt. Efficient is default; parser chooses Precise only for literal `precise`. The limiter sleeps until roughly the last half millisecond; precise spins through the remainder, while efficient substitutes 50-microsecond sleeps. This changes scheduling, not pixels. Compare frame-time variation, p99, actual CPU use and paging; precise may improve timing or waste scarce scheduling time. At cap260 the limiter is bypassed, so this setting cannot explain uncapped results. ## Skip misleading tweaks

- **Translucent batching:** not offered for base Metal flat draws; its file flag is not a meaningful M1 optimization candidate. [Pinned graphics guide](https://github.com/horizon-rust/horizon/blob/c9d474dd9116e84c243f8992d75c11314df56f06/docs/graphics.md).
- **Leaf culling:** every non-off mode can change visible canopy interiors/gaps; outside the unchanged-look requirement. Nonvanilla model packs disable it anyway. Same pinned guide.
- **Smaller texture budget, distance/effect reductions, scaled rendering, TAA/upscaling and performance presets:** change appearance or coverage; not quality-neutral wins. RAM is native unified-memory usage, not a Java heap to tune.
- **Upload budgets:** may spread spikes but delay terrain visibility. Only investigate after measured upload stalls, with backlog and time-to-visible recorded. **Shadow cache:** irrelevant to shader-off base; stale-shadow risk requires separate shader validation.
- **Backend switching:** macOS uses Metal; Windows/Vulkan advice does not apply. Preserve useful disk caches rather than force expensive cold rebuilds.

## Critical measurement correction: AFK throttling

The default `inactivityFpsLimit` is **`afk`**, independently of `pauseOnLostFocus`. With no physical input for more than60 seconds, the effective cap becomes min(configured cap,30); after600 seconds it becomes10. This occurs even with a focused ordinary window. An iconified window, or an exclusive-fullscreen window losing focus, is separately throttled to10. An unfocused ordinary window alone does not trigger that rule. Battery mode separately caps an unfocused window to30.

For controlled local tests, write **`inactivityFpsLimit:minimized`** to the disposable profile's options.txt, keep `batteryMode:false`, and do not minimize the window. This preserves the in-world pixels, simulation and configured foreground cap. Verify `options-get inactivityFpsLimit` before measuring; record the effective limit if available. This is the same AFK mitigation the built-in `--benchmark` startup applies in memory.

The control socket's `bench` handler only resets statistics and stores a reply deadline; `fly` resets statistics and stores the flight. **Neither overrides AFK throttling.** `Game::limit_frame` only bypasses the limiter for frame-count runs or split pacing; it does not exempt control benchmarks/flights. Therefore configured cap260 is not enough to prove uncapped measurement: the earlier statement about pacing being bypassed at260 applies to the **effective** limit, after AFK/battery rules. A near-exact30FPS plateau late in a run is a strong confound, not evidence of a worker or rendering regression. Existing runs without this explicit setting need revalidation before any winner claim.

## First-frame/presentation failure: exact Metal trace

Later root runs reported `acquiring the first frame` with no submission/presentation log, while world/control readiness and subsequent clean quit remained possible. Source supports an **occlusion/failed acquisition hypothesis**, not an established resource or worker failure:

- The acquisition message is emitted only once at gfx.rs5068, then `first_frame` is immediately changed to `Submit`. Thus lack of a second message does not imply it is stuck inside one acquire call. Renderer suspension from invalid/zero drawable size returns before that message on subsequent frames too.
- Pinned vendored wgpu-hal30.0.1 Metal `surface.rs357` finds the CAMetalLayer's hosting NSWindow, reads `occlusionState`, and returns `SurfaceError::Occluded` before `nextDrawable` if its Visible bit (`1 << 1`) is absent. Horizon gfx.rs5101 silently translates Occluded or Timeout into `Ok(false)`, skipping the frame. This can produce the observed one-time acquisition message with a responsive event loop indefinitely. It is actual visibility/occlusion, not just input focus, that matters here.
- Metal configuration disables `allowsNextDrawableTimeout` (surface.rs337); acquire's requested timeout is ignored. A real block inside nextDrawable is possible, but prompt control handling on the same event-loop thread argues against a permanent block during that interval. Existing logs cannot distinguish all paths, including surface reconfiguration or work before the submission log.
- Game idle polls control before requesting redraws. The source explicitly notes that an occluded/locked macOS window may receive no redraw events. Screenshot requests wait for a successfully rendered frame, so they can time out while other controls respond. **A plain ctl bench deadline should still reply while idle/control polling continues**, even if there were zero successful frames; pure repeated Occluded alone does not explain a genuine bench-reply timeout. Confirm the exact failed command before asserting a cause. Scripted flight advancement also requires redraw processing.

Useful next evidence is the actual window visibility/minimized/occlusion state and, for any already authorized live failed run, one main-thread stack sample. A stack in repeated event-loop idle differs from one inside CAMetalLayer nextDrawable or GPU submission. A single startup phase line is insufficient. No device workload was started by this research unit.

The verified official **`--offscreen`** mode removes the surface and draws into a texture; its idle path directly issues RedrawRequested rather than waiting for the compositor. It can isolate renderer/shader correctness and produce screenshots without lowering shader settings. It is **not** an onscreen presentation fix or interchangeable gameplay FPS result; verify its actual target size/backend and label it as offscreen. `--headless` has no renderer and cannot replace this check. No supported env/CLI bypass of Metal's occlusion check was found in the traced code; changing VSync/presentMode does not bypass that pre-acquire condition. Further blind reruns or source rebuilds are not justified by these logs alone.

## Full scene readiness: why wait-ready was insufficient

Root's first two offscreen runs passed the CLI readiness command yet visibly lacked the distant hill; their client columns grew128→206 and103→149 during static measurement. Both must be excluded from a same-coverage worker comparison.

Exact `horizon-ctl::wait_ready` returns at the **first** status with a nonnull player, `pending_chunks == 0`, and `server.loaded != false`. There is no stable-count dwell or coverage target. `pending_chunks` sums the shared work queue length, pending GPU uploads and client packet backlog. `Streaming::pending` only counts queued jobs; it excludes jobs already generating, decorating, finishing, lighting or meshing. A transient zero queue can therefore pass before the full scene exists. `server.loaded` is the client’s PlayerLoaded acknowledgement for terrain near the player, not full-view completion. Moreover `server.chunks` repeats the same client world chunk count; it is not an independent integrated-server measurement.

**A source-derived target exists for this particular local setup:637 columns at radius12.** `lan/hub.rs::tracked` uses `dx=max(abs(x-cx)-2,0)`, likewise dz, then tests `dx²+dz² < radius²`. `requeue_ring` enumerates offsets from `-radius-2` through `radius+2` and queues all tracked unsent columns. For radius12, counting this finite predicate yields exactly637. Integrated startup uses `settings.render_distance.max(2)` as server view distance. With render12, no far ring, unchanged stationary center and ordinary local subscription,637 is the complete subscribed column count, consistent with the earlier fully populated onscreen result. This count is not universal for other distances, server settings or far-view behavior. The4171 resident section count is still an empirical property of this copied world/position, not a generic formula.

For this pair, require client chunks at least637 **before** static timing; stable client count and resident sections across repeated bounded observations; no pending uploads/backlog; no generating/decorating/finishing/lighting/meshing work; and unchanged full hill coverage in the screenshot. `streaming.protos` is retained intermediate data, not necessarily active work, so do not blindly require that count zero. Record time-to-full-coverage as its own result; no FPS benefit is accepted from slower terrain population. Movement changes the subscription center, so the static gate cannot be reused as proof that every flight frame was fully populated.

No offscreen-dependent radius or generation algorithm was found: `apply_settings` always assigns `streaming.radius = settings.render_distance`; normal world-update streaming runs in both modes. Local reception does have a1ms-per-frame chunk-packet handling budget and asynchronous decoding; chunks that have waited50ms can bypass that time budget, but a still-decoding column waits. Thus background contention and frame scheduling can affect population timing without a quality setting changing. A60 cap might free CPU/bandwidth, but this is a candidate to measure, not an established cure.

### Why steady frames do not prove fast terrain generation

In c9, single player has separate server generation/light and client light/mesh pools, each sized by `Graphics::worker_threads` (auto cores−1). In addition, `lan/chunks.rs::warm_pool` independently creates cores−1 chunk encoding helpers and does not consult that graphics setting. On this8-logical-core machine the potential helper concurrency is7+7+7 before render/server/network and Xcode threads, rather than one7-worker pool. This describes potential concurrency, not a measured count of simultaneously runnable threads. Explicit workers3 changes the first two to3+3 while encoding remains7.

macOS render and server threads are raised to USER_INTERACTIVE QoS above four logical cores. `behind_server` lowers helpers only on Linux/Android; its non-Linux implementation returns false. Thus smooth render/tick timing can coexist with a starved or memory-bandwidth-constrained terrain pipeline under competing background work. GPU frame timings do not measure world generation, decoding or total process CPU. Source supports this mechanism; it **does not diagnose the specific30–225second load variance** without existing-run thread/stage/paging evidence.

Generation is also more than637 independent jobs: nearest-first proto chunks need decoration neighborhoods, final columns, lighting and neighboring lit sections before client meshing. In-flight generation is bounded at roughly workers×3; lighting at workers×4; mesh sections at workers×32. Larger pools also retain more per-worker generator/face-cache/mesh scratch until idle. c9 frees those worker-local buffers after5seconds idle and asks the allocator to return free pages once all workers idle, so a Java-like heap cap is not the missing knob. The client processes received chunk packets under a1ms/frame budget, with a50ms backlog escape, but an asynchronously decoding packet can still postpone following events. More FPS does not guarantee the server generated or sent all subscribed columns.

### f42 readiness schema compatibility check before comparison

Exact f42 source confirms status.streaming still exposes the same six active-stage keys **queued, generating, decorating, finishing, lighting, meshing**, plus the seventh retained-data key **protos**. Strict indexing of the six active keys is appropriate; missing fields should be a schema failure rather than silently treated as zero. `pending_chunks` still equals the current streamer's queue length plus pending client uploads and remote packet backlog. The shared job pool did not turn these into global process counters: they remain the window's streamer's fields.

The f42 `lan/hub.rs499` tracked predicate is unchanged from c9: `max(abs(delta)-2,0)` on each axis, squared sum less than radius squared. Thus **637 subscribed columns at radius12 with no far ring** remains source-derived for the same stationary local-world setup. No target-count change is needed for this pair. As before,4171 resident sections is empirical world/position evidence rather than a universal target.

Remaining limitation: `Streaming::busy()` also checks in-flight **viewing** jobs, while `stages()` does not expose `viewing`. Neither the six-zero check nor status.pending_chunks alone proves global/shared-pool idleness; moreover the integrated server's generation is a separate streamer. The new `memory` census has server-generation diagnostics, useful outside the timed interval, but is not needed to redefine the established matched-scene gate. Require637 columns, no backlog/uploads, six active counters quiet, stable resident coverage over a dwell, and the full scene image. Report this as observed scene readiness, not proof every worker or background job is idle. Keep equivalent launch-to-scene timing boundaries and warmup on both versions; if an observed stage fails to settle or coverage differs, retain a visible invalid/blocker result rather than relaxing it to accept an FPS number.
