# Horizon resource migration v4: pruned from v3 (2026-11-05)

## What was built

- `outputs/horizon-converter/2026-11-05-Tanush-f42-v4` is v3 minus every file in a namespace that nothing live can reach, minus the files of the one TRIM verdict from `horizon-layer-shadowing.py`. This is the primary deliverable.
- `outputs/horizon-converter/2026-11-05-Tanush-f42-v4-strict` additionally drops files that no live file references inside namespaces that are reachable only in part. It exists to free the whole emissive cap and is optional.
- `outputs/horizon-converter/2026-11-04-Tanush-f42-v3` was not modified. Both outputs were made with APFS clones and only the changed pack zips were rewritten.
- Free disk after the build was about 4 GiB (`df -g`), so do not build a third copy without deleting something first.

Tools added or changed:

- `tools/horizon-namespace-reach.py` is a read-only report. `python3 tools/horizon-namespace-reach.py <migration dir> [--json]` prints one line per non-vanilla namespace (reachable or not, files, bytes, evidence).
- `tools/horizon_converter_prune.py` holds `analyze`, `trim_candidates`, `effective_map` and `derive`.
- `tools/horizon-convert.py` gained two opt-in flags. Backup: `tools/horizon-convert.py.bak-2026-11-05`. Without the flags nothing changes, and `--game-dir` is still required (a test covers this).
  - `--prune-unreachable-namespaces SOURCE_MIGRATION --output DEST` builds v4.
  - Adding `--prune-unreached-files` builds the strict variant.
- `tests/test_horizon_converter_prune.py` has 5 tests on synthetic migrations.

Every removed path and its reason is in `manifest.json` under `v4_changes` in each output (the `removed` list, one entry per pack and reason). The manifest also records the source manifest hash and the effective-map check.

## How reachability is decided

A namespace counts as vanilla-provided if it is `minecraft` or `realms`, and as carried if a mod asset pack in `mod-asset-packs/*.zip` provides it (227 namespaces). Every other namespace in the resource packs is a candidate. A candidate is reachable when any active text file (JSON, properties, mcmeta, and similar, up to 4 MiB) references `candidate:path`, repeated until no new files are reached. Additional roots:

- A lang file whose keys match live content roots its namespace, because lang files are merged globally. This is why `apothic_enchanting`, `minecraft1202`, `minecraft262` and `vanillabackport` stay.
- OptiFine and MCPatcher sky, colormap, lightmap, animation and GUI property files root the namespace they point into.
- A texture also marks its `.mcmeta` and its `_e.png` emissive companion.
- Overlay directories declared in `pack.mcmeta` are scanned like normal asset roots.

Decisions are per namespace. Per-file counts are informational except in strict mode.

## Emissive overlays before and after

The loader (`native_emissive::load_optifine`) keeps at most 128 minus 32 native entries, so 96 optifine pairs. Bases are sprites sorted before CTM tiles, then by name, so sprite-based glow fills the cap first.

| Migration | Pairs kept | Pairs dropped | Vanilla ore CTM overlays | Notes |
|---|---|---|---|---|
| v3 | 96 | 124 | 0 kinds | cap is filled by block sprite pairs, mostly rail sprites |
| v4 | 96 | 5 | 17 kinds | 5 vanilla CTM overlays still dropped: `nether_quartz_ore` (variant 4) and `redstone_ore` (variants 1 to 4) |
| v4-strict | 87 | 0 | 18 kinds | headroom 9 |

Why v4 still drops 5: the namespace `rays_3d_rails` stays reachable, and 16 of its emissive block sprites remain in the pack even though only 175 of its 8,721 files are used. Those 16 sort ahead of the CTM tiles and take cap slots.

Numbers come from `tools/horizon-layer-shadowing.py` run on each output.

## Which glow now appears

With v4 the New Glowing Ores overlays for vanilla ores (17 ore kinds; the exact list is in the layer-shadowing output for v4) are loaded through the CTM path. In v3 none of them loaded. v4-strict adds one more ore kind (18). Overlays for mod ores (mekanism, create, werewolves) are removed in both, since those namespaces are unreachable.

Existing glow that was already inside the cap (the base-sprite pairs) is unchanged, because the effective map is identical.

## Risks

1. Static regex reachability can miss references built at runtime (string concatenation in a mod, or a property file that names a namespace without `ns:path` syntax). A namespace wrongly judged dead would lose content silently.
2. Carried-mod namespaces are counted as live without checking the mod is enabled. This only makes pruning more conservative.
3. `skybox` is kept because Dramatic Skys sky properties reference it. I found no OptiFine sky loader in the Horizon source, so the 7.3 MiB may be dead weight. Not confirmed.
4. `celestial` and `fabricskyboxes` (41 files) are removed. Horizon has no FabricSkyboxes or Celestial JSON support as far as I could find. If that support is added later, v4 will not have the assets.
5. The alternate icon sets are removed because they are only selectable through Respackopts, which Horizon does not implement. If a user relies on them, the icon choice cannot be restored from v4.
6. Review queues (`review-queue.jsonl`, `raw-review-queue.jsonl`) are copied unchanged and still cite removed paths. They were not regenerated.
7. Strict mode trusts the same static graph at file level, so it has a higher chance of dropping a needed file. It also removes models for rails that dead mods referenced, which is the point, but a missed reference there shows up as a missing-model purple cube. Use v4 first.
8. The v4 pack zips have new hashes. Anything that pins the v3 pack hash (cached provenance, record files) must be refreshed for v4. The manifest keeps the v3 hash in each entry's `v4_prune` record.
9. 5 vanilla ore CTM overlays are still lost in v4 (listed above). Only the strict variant frees them.
